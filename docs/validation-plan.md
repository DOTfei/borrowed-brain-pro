# Validation Plan: Proving Borrowed Brain Pro Helps

> **Current status:** Protocol only. This file is a plan for collecting evidence; it is not evidence that the product already works.

## 1. The problem hypothesis

Independent builders often have a real decision but no durable decision record. They ask an AI for an opinion, receive a persuasive answer, and then lose the assumptions, threshold, and follow-up evidence.

Borrowed Brain Pro is useful only if it helps a builder do something observable that a generic prompt did not: define the uncertainty, choose a falsifiable test, and return with the result.

The claim to test is therefore:

> For a live builder decision, Borrowed Brain Pro helps the owner turn an ambiguous choice into a reviewable Decision Contract and complete a Smallest Useful Test.

This is narrower and more testable than claiming that it makes every decision better.

## 2. Pilot design

Recruit 5–10 independent builders who are currently deciding whether to build, simplify, charge, pivot, or validate. Do not recruit only fans or people who already agree with the project.

For each participant:

1. Record the decision question, options, baseline confidence, current next action, and the evidence already available.
2. Run the same Borrowed Brain Pro workflow: evidence boundary, lens comparison, historical boundary, Smallest Useful Test, and Decision Contract.
3. Record whether the owner changed the next action and why. Keep the original contract unchanged.
4. Ask the owner to run the test in their normal environment.
5. On the agreed review date, record the target signal, threshold result, assumption status, alternative explanations, and next decision.

Use [the Decision Contract template](../templates/decision-log-template.md) before the test and [the Decision Review template](../templates/decision-review-template.md) afterward. Publish only anonymized cases with permission.

## 3. What to measure

| Stage | Observable measure | Why it matters |
| --- | --- | --- |
| Activation | A complete contract with a decision question, assumption, signal, threshold, owner, and review date | Shows whether the workflow is usable, not merely interesting |
| Action | The Smallest Useful Test was actually started | Shows movement from analysis to behavior |
| Return | The owner completed the review record | Tests the core loop instead of one-session satisfaction |
| Evidence | The test produced a measured signal or a clearly documented unknown | Prevents a confident story from replacing evidence |
| Learning | The owner marked assumptions Confirmed, Disproved, or Still Unknown and chose a next action | Shows whether the system improved decision clarity |
| Trust | The owner names one useful output, one wrong or weak output, and one missing piece | Finds failure modes and guards against confirmation bias |

For the first pilot, treat these as operational milestones, not a statistical proof of product-market fit. A practical checkpoint is: at least five completed contracts, most owners starting their test, and several completed reviews with limitations recorded. The exact counts should be reported with the raw denominator, never as an impressive percentage without context.

## 4. What a case study must contain

A case can be labeled **Observed** only when it contains a real decision, the original contract, an executed test, and a review. It can be labeled **Outcome-proven** only when it also contains:

- a baseline recorded before the intervention;
- a measured result against the original threshold;
- the action actually taken;
- alternative explanations for the result;
- a review date and explicit limitations.

The [worked builder case](../examples/real-decisions/indie-ai-writing-assistant-case.md) is **Illustrative**, so it demonstrates the format but does not count toward these milestones.

## 5. Claims we can and cannot make

Before the pilot, we can claim that the repository contains a repeatable decision-analysis protocol, documented historical research, portable bundles, and templates for preserving predictions and reviews.

After the pilot, we may report completion and learning rates for the participants who actually took part. We still must not claim that Borrowed Brain Pro caused a better business outcome unless the design supports that conclusion and the limitations are visible.

Downloads, GitHub stars, positive first-session comments, and a persuasive illustrative answer are useful interest signals. They are not proof that the product solved the decision problem.
